# Changelog

Changes are listed by release, newest first. The sections dated before 0.1.0 record what was built on the way to the first release.

## 0.1.0 (2026-11-16)

The first release.

### Added

- CI on GitHub Actions (`.github/workflows/ci.yml`): `motlab doctor` and `npm test`, the end-to-end renders among them, on `ubuntu-latest` and `windows-latest` with Node 24, the runner's Google Chrome and ffmpeg (8.0.1 from Ubuntu, 9.0.2 from Chocolatey). The runners have no GPU, so Chrome draws in software there. All 30 tests pass on both.
- The viewer runs as a background server. `motlab start` starts it on 4173 (the next free port up to 4190 when something else has 4173) and returns, `motlab stop` ends it (asking it to exit, so a running export closes its Chrome), and `motlab restart` starts it again from the folder it ran in. `motlab edit <project>` now opens the project in the running viewer and ends, starting the viewer first when none runs, instead of staying in the terminal until Ctrl+C; `motlab start --foreground` is the old way. The server's output goes to `~/.motlab/viewer.log`. A stop request from another site's page gets a 403, like the viewer's other writes. Tried on Windows: start in 0.5 s, a second start says it is running, edit, restart from another folder (the menu kept the first folder), stop, edit with no viewer running, and a viewer on 4174 while another server held 4173.
- `motlab uninstall` removes the launchers that run motlab, the two skill folders in every agent folder from `~/.motlab/install.json` (or the agent folders the installer knows), `~/.motlab` and the encoder timings, after listing them and asking. `--yes` skips the question, `--dry-run` only lists, and without a terminal it needs `--yes`. A linked skill is removed as a link. The clone is left. A test runs it in a made-up home folder; a junction made like `--link` does was also removed without touching its target.
- `THIRD_PARTY_NOTICES.md`: the MIT licence of gl-transitions, whose shaders are copied into `src/page/transitions.js` (the MIT licence asks for its text to go with copies), and the licences of what motlab installs or loads from a CDN.
- The README shows the 19-second motlab ad (made with motlab and its skill) as a silent animated WebP, `assets/demo.webp`: 960x540, 24 fps, 4.6 MB. A GIF of the same ad was 7.3 MB at 720 px and 12 fps.
- `bench/run.mjs` takes `IGPU=1` to run only motlab's settings on Chrome's default GPU (the new `bench/motlab-igpu.mjs` leaves out `--force_high_performance_gpu`), which on the test laptop is the integrated Radeon that Remotion and HyperFrames drew on. On the Radeon motlab took 8.0 to 12.0 s at 1080p and 13.2 to 22.5 s at 4K, no slower than on the RTX 3060 except the 4K default (22.5 s against 19.4 s), so the gap to the other two stays about the same.
- `bench/run.mjs` takes `CPU=1` to run the benchmark with Chrome drawing in software (ANGLE on SwiftShader) and CPU encoders only: Remotion `--gl=swangle`, HyperFrames `--no-browser-gpu`, and motlab through the new `bench/motlab-cpu.mjs` with `--encoder sw`. On the test laptop motlab was the fastest at 1080p (19.2 s with 4 workers, HyperFrames 28.3 s, Remotion 46.7 s), but at 4K HyperFrames was faster (43.4 s against motlab's 60.7 s). The GPUs were still in the laptop; a machine without one was not tested. `docs/rendering.md` also notes that Remotion and HyperFrames drew on the integrated Radeon in the GPU benchmark, and that the saved encoder probe keeps one machine.
- `bench/run.mjs` takes `SCALE=2` to render every setting at 4K (motlab `--scale 2`, Remotion `--scale=2`, HyperFrames `--resolution landscape-4k`), with 4K reference stills, into `results-4k.json`.
- `bench/`: one scene (a turning gradient, 160 moving cards with numbers, text) rendered by motlab, Remotion 4.0.543 and HyperFrames 0.9.52 with the same Chrome, timed three times per setting, with SSIM against lossless stills. On the test laptop at 1080p and 300 frames, motlab took 9.5 to 12.6 s, HyperFrames 27.2 s and Remotion 30.7 s at their fastest settings. The table and what was not measured are in `docs/rendering.md`, and the README now shows its results as a table instead of the earlier synthetic benchmark. Not run at 4K or outside Windows.
- `motlab update`. In the clone the command runs from, it fetches the branch from `origin`, lists the new commits, fast-forwards to them and runs the new `install.js --update`, which runs `npm ci`, writes the launcher and copies the skills again to every folder they were installed in. It stops when the clone has changes to tracked files, is not on a branch, or has commits of its own. The installer now keeps where it put the skills, the launcher and `--link` in `~/.motlab/install.json`; for an install from before that file, `--update` finds the skill in the agent folders it knows. `--dry-run` prints the steps. A test runs `install.js --update --dry-run` against a made-up home folder. Tried on Windows in a test clone one commit behind a local bare repository, with a made-up home that had old skills in `~/.claude/skills` and `~/.gemini/config/skills`: the dry run, the update (both skill folders replaced, the record written, doctor Ready) and a second run that said it was up to date. The skill runs it when the user asks for an update.
- The viewer in English as well as Indonesian. It follows the browser (Indonesian when one of its languages is Indonesian, English otherwise), and the last row of the project menu switches to the other language and remembers it. All its text is one table, `TEXT`, and a test checks that every key the page uses is in it in both languages. The server's few error messages are now in English; the page shows its own text for them. Tried in the desktop app's browser on the example project: every label, tooltip, menu, the note card, the range bar and the timeline's key list read in each language, and the version name check worked. The pane was hidden, so the layout was checked through the page's text, not by eye.
- The installer puts the skills where more agents look. `--skill agents` writes to `~/.agents/skills/`, the shared folder that Codex, Cursor, OpenCode, GitHub Copilot, Gemini CLI, Amp and Windsurf read; `--skill antigravity` writes to `~/.gemini/config/skills/`, the one folder both the Antigravity App and its CLI read (the CLI's own `~/.gemini/antigravity-cli/skills/` and `~/.gemini/skills/` are not read by the App); `--skill copilot` to `~/.copilot/skills/`. Targets can be joined with commas (`--skill claude,agents,antigravity` covers all of them), and `--skill-dir <dir>` takes any other agent's folder. The folders come from each agent's docs as of November 2026. A test checks that each skill's name matches its folder and its description is at most 500 bytes.
- A second skill, `skills/motlab-assets`: reusable asset kits built as code, without AI image, video or 3D models. A kit is a folder with `tokens.json`, `style.md`, `kit.json` and each asset's source and outputs, and a video copies it into `assets/kits/`. 2D assets are SVG rendered to transparent PNG at any scale through `templates/asset.html` and `motlab stills` (a 400x600 character to 1600x2400 in 2.6 s). 2D characters are one `parts.svg` plus a `rig.json` of pivots and parents, posed in a scene with `templates/svgparts.js`. A transition is a `transition.js` layer drawn over motlab's hard cut, half in each scene, with a preview page that also writes a PNG sequence with alpha. `scripts/palette.py` reads the main colours of references and measures assets against the kit's colours; `scripts/sheet.py` tiles any images on a checker for review.
- 3D in the asset skill has two paths, and the skill asks which one. The light path needs no Blender: `scripts/mesh_export.py` writes distance-function meshes as GLB and OBJ + MTL with flat PBR colours (a two-part test mug of 194,646 vertices in 2.9 s), and `templates/model.html` renders turntable stills of a GLB through three.js (four 1024 px views in 2.6 s). The main path uses Blender: `scripts/blender/asset3d.py` bakes base colour, roughness, normal and AO maps, exports GLB, FBX and OBJ, renders a Cycles turntable with transparent background, and re-imports the files to check them. On the same mug with Blender 5.2 and an RTX 3060 Laptop: bake 7.5 s, export 1.2 to 2.3 s, four 1024 px views at 32 samples 16.8 s; the GLB, FBX and OBJ came back with the same meshes, materials and 6 texture images. `scripts/blender/check_blender.py` prints the Blender version, the Cycles device, and whether MPFB, a Blender MCP add-on and Rigify are installed.
- `install.js` installs both skills.
- Done notes. Tandai selesai in an open note, or `"done": true` written by the agent in `selection.json`, takes the note off the preview and the timeline and folds it under Selesai at the end of the Catatan list; Buka lagi opens it again. The viewer keeps the file's `done` for notes it did not change, and reads it again on focus, so the agent can mark notes while the page is open. The skill skips done notes and marks each note done once it is applied. Tried on a copy of the example in the desktop app's browser: done and reopened in the card, `done` written into the file while the page was open (picked up on the next click and on a focus event, and not overwritten), and a note in a second version left alone.
- Tooltips in the viewer's style instead of the browser's: a dark label with the shortcut in a key cap, and a list of the timeline's keys when the pointer rests on it.
- Notes in the viewer. A drag on the preview draws a box and a click marks a point, and a card opens under it to type what is wrong there; a range can get a note too. Notes stay until they are deleted, numbered across all versions of the folder, and are listed under Catatan in the side panel and as numbered tags on the timeline. A box or point shows only on the frame it was drawn on. `selection.json` gets `marks`, and each box or point note gets `selection/<n>.png`. The skill reads them and works through them by number. Tried on a copy of the example in the desktop app's browser: a box, a point, a range note and a note in a second version, reloading, opening from the list and deleting (its picture went with it).
- A time range on the viewer's timeline, marked the way video editors do it: a range tool (the button in the play toolbar, or `R`, as in Final Cut Pro) and a drag on the timeline, Shift+drag, `I` and `O` at the playhead (Premiere, Resolve, Final Cut, Frame.io), or `X` for the scene under the playhead (their Mark Clip). Its edges have blue heads like the playhead and can be dragged. It is a light blue band, a range bar next to the play toolbar shows it with Catatan and ×, Play loops inside it, and `selection.json` gets `range: { start, end, scenes }` on the frame grid. Tried on the example project in the desktop app's browser, also at 375 px wide.
- Versions in the viewer. Every `.json` file in a project folder with a `scenes` list is a version, and the second name in the header is a menu of them (`project.json` is "Utama"). "Versi baru dari ini" copies the open version to `project-<name>.json` and opens it. Export renders the open version, and `selection.json` names it as `project`. Tried on a copy of the example with a version that left out the last scene: the viewer showed 2 scenes (6.50 s) and a 720p export wrote `out/iklan-b-tiktok-720p.mp4` in 7 s.
- One viewer for many projects. Each project is at `/p/<folder>/`, and the project name in the header is a menu of the projects the viewer knows: folders with a `project.json` up to four levels under the folder it was started from, and every project opened before (`~/.motlab/recent.json`). A second `motlab edit` adds its project to the running viewer instead of starting one on the next port, and `motlab edit` works without a project. Tried with the example and a copy of it on another drive, next to two older viewers on 4173 and 4174.
- The viewer's export can be cancelled. While an export runs, the Export button is faded with a spinner and a red "Batalkan" button appears under it; pressing it closes the render's Chrome and stops ffmpeg, and the menu says "Export dibatalkan". On the example project at 4K it stopped in 0.3 s during the second scene, with no Chrome process, temp folder or output file left behind. The server route is `POST /export/cancel`, and `renderProject` and `renderVideo` take an `AbortSignal` as `signal`.

- MIT licence, and an install guide, agent install guide and docs for projects, the viewer, the command line and rendering under `docs/`.
- `install.js`: one installer for Windows, macOS and Linux. It runs `npm ci`, writes a `motlab` launcher to `~/.local/bin`, copies or links the skills to the agent skill folders you pick (see `--skill` in `docs/install.md`), and checks the machine.
- `motlab doctor`: checks Node, Chrome, ffmpeg, ffprobe, the npm packages and the skill's Python packages, and prints how to get what is missing.
- `skills/motlab/requirements.txt` for the skill's Python scripts.
- CONTRIBUTING, SECURITY, CODE_OF_CONDUCT, AGENTS.md, ROADMAP and GitHub issue and pull request templates.
- Skill: `get_sfx.py` searches Openverse for openly licensed sound effects (CC0 by default, or any licence that allows commercial use), downloads the chosen ones and keeps a `CREDITS.md` with a credit line for each. Without a key Openverse allows 20 requests a minute and 200 a day (its rate-limit headers on 2026-11-13). It retries with `certifi` when the Windows certificate store rejects a valid chain, as it did for `cdn.freesound.org` on the test laptop.
- `mix.py`: a cue can name a `role` (`hit`, `whoosh`, `riser`, `click`, `ui`, `pop`, `tap`, `key`, `tick`, `ambience`) that sets its level and anchor. The levels follow the [Clipwing real-sfx skill](https://clipwing.pro/skills/real-sfx) (hit −4, whoosh −9, riser −12, click −14, ambience −24 dBFS peak).
- `mix.py --voice <file> [--duck 9]` turns the effects down while the voice speaks. On a test mix with two seconds of synthetic speech, a whoosh under speech came out 9.0 dB lower and a click 0.6 s after it about 0.5 dB lower.
- `mix.py` warns about one recording 5 or more times in a row and about `tick`, `key` and `pop` runs closer than 66, 87 and 114 ms (the spacings in earshot's launch kit), and ends with up to five "listen by ear" moments for the user.
- Skill: when earshot is installed (its CLI or MCP tools), the agent uses it to shortlist sounds from a library by what they are, measure the mix (LUFS, true peak) and render a missing sound from code. It asks before fetching earshot's 1.1 GB of models. Without earshot nothing changes. Not tested with earshot installed: the laptop used for this change does not have it.
- Skill: `template-three.html` for real 3D with three.js 0.186.1 (a GLB or glTF model, or a placeholder box, on a shadow floor with a 2D title over it; model animations through `mixer.setTime(t)`), and `template-p5.html` for generative graphics with p5.js 2.3.4, with `references/engine-p5.md` on keeping p5 frames independent of each other. Both load the library from jsDelivr, so rendering them needs the network. Stills rendered forwards and in reverse were identical byte for byte, and a 3-scene project with both rendered at 1080p and 4K and played in the viewer, on the test laptop (RTX 3060 Laptop). Not tested with a real product model or in p5's WebGL mode.
- Transitions between scenes. A scene in `project.json` can be `{ "file": ..., "transition": { "type", "duration", "ease", "params" } }`, and the scene before turns into it through one of 11 shaders from gl-transitions 1.43.0 (MIT): `fade`, `fadecolor`, `Directional`, `directionalwipe`, `directionalwarp`, `circleopen`, `CrossZoom`, `crosswarp`, `SimpleZoom`, `LinearBlur`, `cube`. The two scenes overlap for the transition, so the video is that much shorter. The render draws it as a part of its own (`__motlab/transition.html`), the viewer mixes the same two canvases with the same code (`src/page/transitions.js`), and the timeline marks the overlap with a bowtie. On the example project, a transition frame in the viewer and in the 1080p MP4 differed by 1.37 levels of 255 on average. `selection.json` gets a `transition` field inside one.
- `/__motlab/motion.js` for scene pages: easings, CSS `cubicBezier`, exact springs (`spring({ stiffness, damping, mass, velocity })`, solved in closed form so frame order does not matter), keyframes (`tween`), `stagger` and `motionBlur`. `test/motion.test.js` checks them.
- Cut lists for talking heads: `skills/motlab/scripts/cut_pauses.py` cuts the pauses out of a recording with ffmpeg `silencedetect` into `cuts.json`, and writes the voice with the same cuts. `/__motlab/cuts.js` plays the list in a scene with alternating punch-in zoom, an eased glide between framings, a slow drift and optional dissolves. On 40 s of a talking-head take: 10 parts, 38.64 s to 33.47 s, and the cut voice was the length of the list to within 10 ms, with and without a dissolve.
- Skill: `references/motion-and-libraries.md`, with tested ways to drive GSAP 3.15.0, Anime.js 4.5.0, Lottie (lottie-web 5.13.0) and Theatre.js core 0.7.2 from `renderAt(t)`. Each moved a test box to the expected position in forward and reverse order, in stills and in the viewer.
- A banner at the top of the README (`assets/banner.svg`). Its text is outlined to paths from Syne, Instrument Sans and IBM Plex Mono (all OFL), so it looks the same on GitHub without loading fonts.

### Fixed

- Renders made while Chrome draws in software (SwiftShader, or a machine without a GPU) had shifted colours: Chrome writes such frames as full range YUV, and every file was tagged limited range, so `#30E2A8` decoded as (41, 243, 179) instead of (48, 226, 168). The range now comes from the encoder's `decoderConfig`, and ffmpeg writes it into the container and the bitstream. On a GPU nothing changes. Found by the first CI runs, reproduced and checked on the test laptop with SwiftShader. motlab's SSIM in the benchmark without a GPU went from 0.980 to 0.982 and 0.983 at 1080p, and from 0.988 to 0.991 and 0.992 at 4K.
- Scene transitions failed with "scene transitions need WebGL2" on a Linux machine without a GPU. Chrome now gets `--enable-unsafe-swiftshader`, so WebGL falls back to software there; with a GPU it changes nothing.
- Two viewer tabs on one project lost notes. Each tab saved its whole list, so a note made in one tab was dropped when the other saved, and both gave their new note the same number, the second overwriting the first one's picture. A save now names the notes the tab deleted, the server keeps the rest (`mergeNotes` in `src/editor.js`, tested in `test/notes.test.js`) and moves a new note to the next free number when its number was taken, and the page takes in the file's notes after every save and on focus. Notes get an `id`; notes from before ids are matched by number. Tried with two tabs in a windowed Chrome: notes 1 and 2 from the two tabs, each listed in both after a focus change, and a delete in one tab that the other did not undo. A running viewer keeps the old code until it is started again.
- A project whose scenes had different canvas sizes rendered without a word and made an MP4 that changed resolution partway through (1920x1080, then 1280x720, then 1920x1080 in the test). `motlab render` and Export now stop with an error that names the scene and both sizes. `test/render.test.js` checks it.
- The render put mono audio files 3 dB lower than the viewer plays them. ffmpeg's up-mix to stereo lowers a mono channel by 3 dB on each side, while WebAudio copies it to both at full level. Mono files now go to both channels at full level in the render too. On the example project (all three files are mono) the viewer, recorded off its audio graph, and the render now differ by 0.02 dB instead of 3.0 dB. Renders of existing projects with mono files get 3 dB louder. `test/render.test.js` checks the level.
- A page whose `window.ready` never resolves made `motlab render`, `video` and `stills` wait forever in silence. They still wait, since a heavy page can take long, but print "Still waiting for window.ready after 30 s" with the page and its errors.
- `template-three.html` asked for `PCFSoftShadowMap`, which three.js 0.186 has removed; it fell back to `PCFShadowMap` with a console warning for every scene. It now asks for `PCFShadowMap`, so the shadows are as before without the warning.
- `puppet.js`'s header left out the last two arguments of `draw` (`cw`, `ch`, the target canvas size).
- The viewer's Cancel button did nothing. The page asked for `export/cancel` relative to `/p/<project>/`, the server only answers `/export/cancel`, and the 404 was swallowed, so the render ran on and the button stayed on "Cancelling…". The page now asks for `/export/cancel`. Tried in the desktop app's browser on the example project at 720p: cancelled 4 s in, during scene 1, it stopped in 0.8 s with "Export cancelled" and no file left in `out/`.
- `get_sfx.py search` failed with HTTP 401 whenever `--max` was given or `--n` was above 20: without a key Openverse refuses a `page_size` above 20 ("page_size may not exceed 20 for anonymous requests"), and the script asked for 40. It now asks for pages of 20, reads up to 3 of them with `--max`, lists at most 20 sounds, and prints the API's message instead of a traceback when a request fails. ### Security

- The viewer's server only accepts writes (every POST: `/selection`, `/versions`, `/export`, `/export/cancel`, `/open`) from its own page or from `motlab edit` (no Origin). A request from another origin, or with a host name other than `127.0.0.1`, `localhost` or `[::1]`, gets a 403, so another site open in the browser cannot write `selection.json` or start an export.
