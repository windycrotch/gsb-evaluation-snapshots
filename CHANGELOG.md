# Changelog

Changes are listed by release, newest first. The sections dated before 0.1.0 record what was built on the way to the first release.

## 0.4.0 (2026-11-21)

### Added

- The viewer's Export menu sets how many scenes render at once, as `motlab render --parallel` does: Otomatis (the server's own pick for its machine, 3 or fewer) or 1 to 4. A line under it says what the pick does, and turns red above the suggested number. Before, Export always used the automatic number.
- The viewer shows a saved scene without a reload. While a page is open, the server watches the project folder and sends each saved file over an event stream, and the page loads again only the scenes whose pages loaded that file (from the browser's resource timing), in the background, so the preview keeps the frame it shows until the new page is ready. A scene that does not load keeps its old page loaded, and the preview shows the reason in its place (or, off screen, a message). A change to the project file, its audio or a transition file reloads the whole page, after an open note or the Export menu is closed. Tried in Chrome on a copy of `example/`: one scene's change loaded that scene only, a change to the shared `lib.js` loaded all three, and a syntax error kept the old page. `test/live.test.js` checks the event stream. Not tried: through Caddy on a real VPS.
- `motlab working <project> [text] --note 3,5 --scene 2` shows in the open viewer what the agent is working on. Those scenes are not shown while it works: a blank pane takes the frame's place, with a small loader drawn from the timeline (scene tiles filling as a playhead sweeps across them) and "Agent sedang bekerja", paused or playing, and no note can be drawn on it. It is the only moving sign; the scene list, the timeline and the notes name it in still text. `--done` brings the scene back, and so do 10 minutes without a word or a saved file. With no viewer or no page open it says nobody sees it and still succeeds. The skill runs it around every revision round, and no longer asks the user to reload.
- A pencil for notes in the viewer: `P` or the pencil button in the new note tools next to the play toolbar draws freehand on the preview, and `M`, Escape or the box button goes back to boxes and points (P as Frame.io's annotation key, M as Photoshop's marquee; R stays the range). More strokes go into the same note until it is closed; the card's undo arrow or Ctrl+Z takes back the last one, and Shift+Ctrl+Z or Ctrl+Y puts it back. A drawing is saved in `selection.json` as `stroke` (lists of `[x, y]` points in the scene's pixels, simplified to within 0.75 screen pixels) with `box` around it, and in `selection/<n>.png`. Tried in Chrome with the mouse and with pointer events: a circle of 127 events kept 27 points, undo and redo, and moving a drawing. Not tried: a pen or a finger on a real touch screen.
- `motlab help` prints the list of commands, like `motlab --help` and `-h`. Before, it stopped with "unknown mode". `test/cli.test.js` checks all three and that a wrong command still fails.
- Steps for an agent that puts the viewer on the user's VPS (docs/install-for-agents.md, step 6): the domain and its DNS, a password the user writes into a file only they can read, Caddy, which ports to open and which not, a systemd user service (in docs/viewer.md) and how to check it. The skill and AGENTS.md point to them. Not run on a real VPS yet.
- `motlab doctor` shows whether earshot is there, the optional tool the skill uses to listen to sound. It is `ok` when the CLI and its models are there, and `warn` with what to do when the CLI is missing or its models (about 1.1 GB) are not downloaded. It never makes the doctor fail, and motlab never installs it. The check runs `earshot doctor`, which took 0.9 s on the test laptop and loads no models. Checked with earshot 0.4.1 there, and `test/doctor.test.js` covers the missing, no-models and ready cases with faked output. Not tried: a machine where earshot is installed but its models are not downloaded.
- `"qp"` and `"codec"` in `project.json`, and `--qp` and `--codec` on `motlab render`, set the file size against quality for a project, and the viewer's Export uses them too. Before, only `motlab video` took them. `"qp": 22` made an 8 s 4K render of a busy page 30% smaller (12.49 to 8.68 MB) with SSIM 0.9964 to 0.9960 and VMAF unchanged at 99.98. docs/rendering.md has a File size section with the measurements: HEVC, a second ffmpeg pass (NVENC HEVC, x264, SVT-AV1), keyframe spacing and a higher QP for P-frames were measured too, and none beat raising the QP at the same quality. The default stays QP 18. `test/render.test.js` checks that the QP reaches the encoder, that a wrong value is refused, and that a part made at another QP is not reused from the cache.
- The viewer can run on a server and be opened at a domain of your own: `MOTLAB_VIEWER_PASSWORD=... motlab start --domain viewer.example.com`, behind a reverse proxy such as Caddy for HTTPS. It still listens only on `127.0.0.1`. Every request then needs a login, whatever Host header the proxy sends: a password of at least 12 characters, which gives a 30-day session cookie that is HttpOnly, Secure and SameSite=Strict. Writes must come from the viewer's own page on the domain, and after 5 wrong passwords in a minute the login waits. `motlab edit`, `stop` and `restart` on the server send a token the viewer writes to `~/.motlab/viewer-token` and removes when it stops. docs/viewer.md shows the Caddyfile and the Tailscale option. Checked: `test/access.test.js`, the real viewer with curl sending the domain's Host header, and Chrome on localhost (sign-in, a wrong password, saving a click, `motlab edit` and `stop` through the token). Not tried: a real VPS behind Caddy with a real certificate.
- A transition can be a layer drawn over a hard cut: `"transition": { "layer": "assets/kits/acme/transitions/swish/transition.js", "duration": 0.6 }`, such as the asset skill's `transition.js`. The module's `draw(ctx, p, W, H)` covers the last half of the duration of the scene before and the first half of the next, in the page's own pixels. `p` reaches 0.5 at the cut, and the video keeps its length because nothing overlaps. Before, each of the two scene pages had to draw its half by hand. It is an option for when the user asks for one: the skill still designs each transition frame by frame in the scenes by default. The render draws it on the transition part and the viewer over the preview, and the module is part of the cache key. A note on a frame inside it records `transition: { layer, from, frame, frames }`. Checked: `test/render.test.js` renders a layer at `--scale 2` and checks the frame count and where it is drawn on both sides of the cut; `test/motion.test.js` checks how the frames are split; the asset skill's swish covered the whole frame at the cut and showed the same picture 0.2 s after it in the viewer and in a 1080p render. Not tried: a layer that loads its own images or fonts.
- `motlab render` and the viewer's Export render several scenes and transitions at once, each in its own Chrome, after the first scene has picked the encoder. `--parallel N` sets how many; the default is 3, but never more than one per 4 CPU threads or per 1 GB of free memory. If a part fails while several run, the finished parts are kept and the rest are rendered one at a time, so a machine that cannot run three still finishes. Each part's log is printed in one piece when it ends. On the test laptop (Ryzen 7 5800H, 16 threads, RTX 3060 Laptop), a project of 12 two-second scenes with 11 transitions went from 78 s to 45 s at 1080p and from 93 s to 53 s at 4K; four at a time was no faster than three. The example project went from 12.7 to 13.1 s to 8.9 to 9.6 s at 1080p, with an identical MP4. `test/render.test.js` renders a four-scene project three at a time and checks the frame count and the colours of every scene and transition, then breaks one scene and checks that it is tried again alone and its error is the one reported. Not tried: a machine with fewer threads or less memory, and a GPU that runs out of encoder sessions.
- A scene transition can come from a `.glsl` file in the project, as `"type": "transitions/swipe.glsl"`. The file is a gl-transitions shader: `vec4 transition(vec2 uv)` with `getFromColor`, `getToColor`, `progress` and `ratio`. Its uniforms (float, int, bool, vec2 to vec4, ivec2 to ivec4) take their defaults from the comment after them, as gl-transitions writes them, and `params` sets them. The viewer and the render compile the file before the first frame and report a mistake with its line in the file. The file's contents are in the cache key, so `--only` renders an edited transition again. The skill's motion reference says how to write one, and how to match a transition from a reference video by laying frames from both on contact sheets. Checked: the 11 built-in shaders parse back to the uniforms and defaults listed with them; `test/render.test.js` renders a project with a shader file at its defaults and with `params`, and checks that a mistake on line 3 is reported on line 3; the wipe from the docs looked the same in the viewer and in a 1080p render, and the viewer showed a compile error with its line. Not tried: shaders copied from gl-transitions beyond the 11 built in, and matching a real reference video.
- One recording can be split over several scenes by section, with captions from a transcript. `cuts.json` takes `"sections": [{ "name", "from" }]` in seconds of the recording (`cut_pauses.py --sections hook=0,demo=41.5` writes them and prints where each lands), and `cutList(cuts, clip, { section: 'demo' })` plays that section from time 0: it starts at the cut nearest its `from` and runs to the next section's cut, so the section scenes add up to the cut voice. `edit.captions(transcript)` takes Whisper's JSON with word times, or a list of `{ text, start, end }`, drops words that were cut out or lie outside the section, and returns caption lines in the scene's time, broken at pauses, sentence ends and a character limit. motlab does not transcribe. Checked: `test/cuts.test.js` (new) checks section starts and lengths with and without a dissolve and how captions are placed; `test/render.test.js` renders two section scenes of one grey-coded recording and checks all 24 frames; `cut_pauses.py --sections` on a made-up take matched `cutList`. Not tried: a real Whisper transcript and a real take split into sections.
- With no system Chrome, motlab uses the newest Chromium that Playwright downloaded, from Playwright's folder (`~/.cache/ms-playwright` on Linux, `~/Library/Caches/ms-playwright` on macOS, `%LOCALAPPDATA%\ms-playwright` on Windows, or `PLAYWRIGHT_BROWSERS_PATH`), so `motlab doctor` passes without `CHROME` on a machine set up for Playwright (issue #8). The folder names come from Playwright's own code, and a test checks the lookup on folders made for it. Not tried: a real Playwright download found this way. The render in issue #8 used that Chromium with `CHROME` set.
- `motlab render --only 3` (or `--only 3,5`) re-renders only the scenes you name, plus the transitions touching them, and takes the rest from the cache in `~/.cache/motlab/parts` (`%LOCALAPPDATA%\motlab\parts` on Windows, or `MOTLAB_CACHE_DIR`), which a full render leaves behind. A scene with no cached part is rendered, so `--only` on a project that was never rendered works like a full render. A finished render removes the cached parts it did not use, so the cache holds the last render only and `--only` needs the same `--scale` as that render. The cache key holds the motlab version, so parts made by an older version are rendered again after an update. The cache keys on the scene page itself: a file the scene loads changing (a shared script, a font, a picture) is not noticed, so render the whole project again then. Checked on the example project (3 scenes, 9 s, 1080p) on Ubuntu 24.04 with no GPU, SwiftShader, while other builds were running on the same machine: a full render took 44 to 49 s, `--only 3` took 17 to 24 s. The --only output differs from a full render by the same amount two full renders differ from each other (average PSNR 68.9 dB in both cases, from the encoder's run-to-run variation). `test/render.test.js` renders a project, changes one scene, re-renders with `--only` and checks the frame count, the cached log line, the colours of the cached, transition and re-rendered frames, and that the old parts are gone.

### Fixed

Before, a scene with a script error stopped the page with "Cannot read properties of undefined (reading 'width')", which said nothing about the scene. The broken scene is now kept as a 2 s scene with a blank thumbnail, the preview shows why in its place (no `renderAt` and `TOTAL`, no `<canvas id="c">`, or `ready` not resolving within 60 s), and a save that fixes it loads it as usual. Tried in Chrome with a syntax error in scene 2 and then in scene 1 of a copy of `example/`: the project opened both times at 1920x1080, and fixing scene 2 brought back its 3.50 s and the 9.00 s total.
- `motlab stills` at 4K stopped with "TypeError: Failed to fetch" after 109 stills of a busy 1920x1080 page at `--scale 2` (4.6 MB PNGs, about 500 MB in all), every time. The page uploaded each still as a Blob, and Chrome frees a Blob only when garbage collection runs, which Blob memory does not trigger. ## 0.3.0 (2026-11-18)

### Added

- `--skill hermes` for setup and the installer puts the skills where Hermes Agent reads them: `skills/` in its home, which is `HERMES_HOME` when that is set, else `~/.hermes`, or `%LOCALAPPDATA%\hermes` on Windows. Hermes does not read `~/.agents/skills` unless it is added to its config. `--skill muse` is another name for `agents`, because Muse Code reads `~/.agents/skills`. The README and the install docs list both agents. Checked on the Windows laptop with a test home: setup copied both skills to the two folders, and `motlab uninstall` removed them again. Neither agent was installed here, so neither has loaded the skills yet.
- Full screen in the viewer has a player bar. Before, it showed the preview alone. Now one white card runs along the bottom of the full-screen preview, as in the cinema viewer of DaVinci Resolve or Frame.io: a scrub bar split into the scenes, with the open notes' numbers above it and a range as a blue band, then the time and the scene on the left, previous, play and next in the middle of the screen, and a button on the right that leaves full screen. Click or drag the scrub bar to move in time, rest on it to see the time, click a note's number to open it; the arrows step a frame anywhere in full screen. The timeline and its range, zoom and timeline buttons stay out. So that it covers no part of the frame, the bar stays hidden, also while paused, and comes up while the pointer is in the bottom 120 px of the screen, like an auto-hidden taskbar; it also shows for 2.5 s on entering full screen and after Space, the arrows, Home or End, and never while a note is drawn or moved. While the video plays and the pointer rests, the cursor hides too. `F` opens and closes full screen, tooltips show there too, and the full-screen button no longer keeps the focus, so Space plays instead of leaving full screen. Checked in a windowed Chrome on the Windows laptop over the DevTools protocol, on a 1920x1080 screen: a click at the middle of the scrub bar went to 00:04.50 of 9 s, a drag to 80% to 00:07.20 and the scene name followed, the play button sat at the middle of the screen whatever the scene name, the arrows stepped one frame, a note's number opened that note, the bar hid 2.5 s after entering while paused, came up with the pointer near the bottom and stayed there, went when the pointer left, showed after an arrow key, stayed down while a box was drawn to 40 px above the bottom edge, and hid with the cursor while playing, a note could be drawn and moved, and the exit button brought the timeline back. Headless Chrome refuses full screen, so this has no automated test.
- An open note's box can be moved by dragging inside it and resized by dragging a corner or an edge, and an open point can be dragged. Before, a box in the wrong place had to be deleted and drawn again. The box stays inside the frame and keeps its number, text and frame, and its picture in `selection/` is drawn again.
- Delete all done notes, under the unfolded done notes, deletes the open version's done notes and their pictures in one go, after a second click within 4 s. Both note changes were checked in headless Chrome on the example project: moving, resizing from a corner, flipping a box by dragging a corner past the other one, dragging it off the frame, moving a point, the cursors over each part, a new box drawn over a closed one, and clearing two done notes while an open one stayed.
- The viewer has a phone layout. Held upright, it is one column that scrolls: the preview across the top instead of a small preview in a large grey area, the play toolbar with the full-screen button, the timeline, then the notes, scenes and audio, notes first, instead of a side drawer. The header keeps the project and its version, and Export shows its icon. The menus open across the width under the header, and the open note's card sits across the bottom of the screen above the keyboard. Held sideways (below 500 px high), the side panel starts closed and floats, so the preview went from 135x76 to 286x161 px at 844x390. Menus fit the screen's height, and on a 360 px phone the toolbar's buttons shrink to 38 px so it fits. In full screen on a touch screen, a tap near the bottom brings the player bar up, and a drag from there still draws a box. Checked in headless Chrome with a phone emulated at 390x844, 360x740, 844x390 and 740x360 (no sideways scrolling, every menu inside the screen, a note drawn with touch events and saved), the tap in full screen in a windowed Chrome with touch emulated, and the desktop layout unchanged. A real phone has not been tried.

### Fixed

- Running motlab as root, as in a container or on a VPS logged in as root, failed at the first scene with "Chrome exited early (code 1): Running as root without --no-sandbox is not supported", because Chrome refuses to start as root and motlab passed no such flag. Chrome now gets `--no-sandbox` when motlab runs as root, and only then; motlab only opens the user's own pages. Checked on Ubuntu 24.04 as root, no GPU, Google Chrome 157: `motlab render example --scale 1` went from failing at once to a 9 s, 1080p render in 13.6 s (8.5 s on a repeat run, with the encoder probe cached), and `npm test` passed 34/34. Not tried: a non-root user in a container where Chrome's sandbox still fails.
- Footage in WebM or MKV showed some frames one frame late: at 30 fps every third frame (2, 5, 8 and so on) was the one before. These containers store timestamps in whole milliseconds, so a frame due at 0.0667 s is stored at 0.067 s, and `clip.frame(t)` did not count it as shown yet. `footage.js` now rounds the time it is asked for to the millisecond for these two containers, and MP4 and MOV work as before. Checked on the Windows laptop with clips made by ffmpeg in which every frame is a different grey: VP9 in WebM and MP4, H.264 in MKV, MP4 and MOV, at 24, 25, 29.97, 30 and 60 fps, rendered at 30 fps and at the clip's own rate, 40 cases, every output frame the source frame due at that time (12 of the 40, all WebM or MKV, were wrong before). Stills in a jumbled order and stepping frame by frame in the viewer showed the right frames too. `test/render.test.js` renders a VP9 WebM and checks every frame. Not tried: footage filmed on a phone in these containers.

## 0.2.2 (2026-11-17)

### Fixed

- 0.2.1's setup dropped every copy of Node's folder from the front of PATH before checking whether npm's command folder was on it. That is right on Windows, where nvm 2.0's shim puts it there, but on macOS and Linux nvm puts Node's folder first in the terminal itself, and it is npm's global folder, so setup would have written an unneeded launcher to `~/.local/bin` and asked to add that folder to PATH. Outside Windows only the copy npx adds is dropped now. The check is in `src/userpath.js`, and seven PATH cases in `test/install.test.js` (Linux nvm directly and through npx, Linux system Node, a folder really off PATH, nvm for Windows directly and through npx, Node from nodejs.org) cover it on the CI runners. The 0.2.1 version failed both Linux nvm cases.
- A scene transition whose WebGL context was lost failed with "transition fade: null", because the shader logs come back empty then. It happened twice in three CI runs on the Ubuntu runner, where Chrome draws with SwiftShader, at the first shader compile. The mixer now builds a new canvas and context and draws the frame again, and only a second loss stops the render, with a message that says so. A loss that draws nothing without an error is caught too, by checking the context after the draw. Checked in Chrome on Windows with `WEBGL_lose_context`: a context lost once drew the frame (the right colour), one lost every time stopped with the message, and a normal one drew as before. CI then passed three runs in a row on both runners. Why the runner loses the context was not found; a GPU watchdog during a slow software compile is a guess.
- When mediabunny is not installed, as in a clone where `npm ci` was never run, the renderer said only that the page "failed to fetch dynamically imported module ... mediabunny.mjs" before it fell back to the raw bitstream. It now says mediabunny is not installed and to run `npm ci` in the engine folder. Seen on a Linux VPS where the tests ran in a fresh clone; checked on Windows with a copy of the engine that has no `node_modules`.
- `motlab doctor` told a user missing Python packages to run `pip install -r skills/motlab/requirements.txt`, a path that only works from a clone. It now prints the full path. Seen on the Linux VPS after an npm install.

### Changed

- When Chrome is missing on Linux, `motlab doctor` prints the commands that install Google's `.deb` on x64 Debian or Ubuntu, and says the Chromium snap can fail headless, instead of "install Google Chrome or Chromium from your distribution". On other processors it says to use the distribution's Chromium, not the snap. Checked by printing the hint with the platform set to Linux x64 and arm64 on the Windows laptop; the commands have not been run on Linux.
- The README's install section lists the setup command for each agent (Claude Code, the agents that read `~/.agents/skills`, Antigravity, several at once, any other folder) instead of a folded list of options.

Tried on Windows 11 with nvm for Windows 2.0 and this laptop's own PATH: `npm install -g` of the packed tarball, then `npx @motlab/cli setup` from a test home wrote the launcher when npm's folder was off PATH and none when it was on PATH. On a Linux VPS (Ubuntu, Xeon Platinum 8255C, 2 cores, 8 GB, no GPU, Node 24.22.3 with npm's prefix in `~/.npm-global`), with a tarball packed from this branch: `npx @motlab/cli setup --skill none` wrote no launcher, `which motlab` found npm's own command, `doctor` was ready, the example rendered at 960x540 with SwiftShader and the software H.264 encoder (about 180 to 215 fps, 1.5 to 2.3 s a scene), and after `npm ci` in a clone `npm test` passed. Not tried: macOS, and nvm on Linux outside the tests.

## 0.2.0 (2026-11-17)

### Added

- motlab is on npm as `@motlab/cli`, in the npm organization `motlab`, since the name `motlab` alone was taken there by an unrelated package. The command is still `motlab`. `npm install -g @motlab/cli` installs the engine and the command. The package holds the engine, the skills, the example project and the docs (90 files, 943 kB packed); `bench/`, `test/` and the README images stay in the repository.
- `motlab setup` copies the skills to agent folders after an npm install. It runs `install.js --skills-only`, so it takes the installer's skill options (`--skill`, `--skill-dir`, `--link`, `--update`, `--force`, `--dry-run`) and ends with `motlab doctor`.

### Changed

- From an npm install, `motlab update` asks npm for the newest version and prints the commands that get it (`npm install -g @motlab/cli@latest`, then `motlab setup --update`), and `motlab uninstall` says to finish with `npm uninstall -g @motlab/cli`. A clone works as before.
- The README installs with npm first; the clone and `install.js` are under "From a clone instead".

### Security

- The viewer's server only accepts writes (every POST: `/selection`, `/versions`, `/export`, `/export/cancel`, `/open`) from its own page or from `motlab edit` (no Origin). A request from another origin, or with a host name other than `127.0.0.1`, `localhost` or `[::1]`, gets a 403, so another site open in the browser cannot write `selection.json` or start an export.
