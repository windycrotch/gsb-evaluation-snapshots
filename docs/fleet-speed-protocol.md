# 联盟城战智能省钻：协议核对与策略

核对日期：2026-11-17。依据本机微信缓存第76版客户端、对应 protobuf 和本机配置表；没有为了本次分析连接游戏或执行真实钻石加速。

## 已验证的计费与请求

| 操作 | 客户端实际请求 | 计费与效果 |
| --- | --- | --- |
| 维修加速 | `SpeedUpRepairRequest { buildingId, speedUp: { type: 1, useNum: 0 } }` | 剩余秒数除60向上取整，按全角色累计维修加速分钟分段计费；钻石加速一次完成剩余维修 |
| 行军加速 | `SpeedUpFleetRequest { buildingId }` | `WorldParamCfg` 的“行军加速消耗”，本次核对为30钻；客户端说明为速度翻倍 |
| 累计计费状态 | `SCSpeedUp.data[] { type, minutes }`，维修对应 `type=4` | 所有舰队及城战、硅矿共享这一累计值，不是每队独立费率 |

请求没有“目标剩余时间”“最高扣款”或“只买若干分钟”的字段，也没有配套的加速报价接口。因此只能在发送前核算和限制本地预算，不能把预算上限交给服务器原子执行。`useNum: 0` 是客户端钻石模式的实际用法，不能把它改成希望购买的分钟数。

`SpeedUpCostParam` 虽有道具、广告枚举，共用弹窗也有道具处理代码，但舰队维修使用专门的显示分支，广告分支没有舰队维修类型。本次没有验证出可用的维修道具或免费广告方案，不据此发送试探性请求。

### 维修阶梯

当前 `SpeedUpRubyCfg.fleet`：前60累计分钟每分钟10钻；60分钟起11钻，之后每增加20累计分钟再加1钻，240分钟起最高20钻。跨档位逐段计算，不把整笔费用统一乘旧档或新档。

| 加速前累计分钟 | 剩余2:01（计3分钟） | 剩余1:59（计2分钟） | 少花钻石 |
| --- | ---: | ---: | ---: |
| 0 | 30 | 20 | 10 |
| 59 | 32 | 21 | 11 |
| 60 | 33 | 22 | 11 |
| 240 | 60 | 40 | 20 |

累计59分钟再加速2分钟的费用是 `1×10 + 1×11 = 21`，不是20或22。等待跨过一分钟边界不仅减少本次费用，也减少后续累计档位的增长。

## 智能省钻的选择

每队的维修与派遣分别配置智能省钻开关及等待上限，位于各自加速选项内部。可以关闭舰队1的维修省钻、保留其派遣省钻，也可以只对舰队2维修省钻；互不影响。旧版共用开关与等待秒数兼容迁移到两项，显式设置的新字段优先。

### 维修：有限短等，少计一个完整分钟

- 每队的维修智能省钻独立开关，最多主动等待默认5秒，可设1–60秒。
- 临近分钟进位边界且等待不超过配置时，等到边界下1秒再重新读取、重新报价。例如2:01等2秒到1:59，给倒计时边界留余量。
- 如果即将自然达到“不加速阈值”，直接等到阈值，省掉整笔加速费用。
- 剩余时间已经在阈值以内，不再花钻。维修阈值不是“付费后恰好停在这个秒数”，因为钻石维修是一次完成。
- 等待期间其他队伍可能推进费率，实际发送仍按最新共享累计量和预算复查。调度串行繁忙时可能晚于预计时刻检查，不能承诺精确到秒执行。
- 同一次维修只短等一次，以持久记录保存固定截止时间。跨过第一个计费边界后不会继续等待下一分钟；推送、重连或跨日都不会重新计时。等待标记不占钻石预算或舰队锁，其他队伍仍可处理。

### 行军：必要的付费步骤先做，最后短等

行军不是按分钟收费，每次固定付费。先加速、接近目标后再短等，比为了少点一次而在出发时等待更快；不需要把等待提前到更大的二倍、四倍时间边界。

忽略请求耗时，设剩余时间为R、停止阈值为T、最多短等W秒。按保守的整数向上取整模拟，最少付费次数是满足 `ceil(R / 2^k) <= T + W` 的最小非负整数k。先完成这k次，再等待到T即可。同样一秒自然等待，放在加速后比放在加速前更有效。

例如R=242秒、T=60秒、W=5秒，按向上取整模拟：`242 → 121 → 61`，付费两次后等1秒即可，合计60钻；无需为了最后1秒再付30钻。服务器实际的时间戳取整方式没有通过付费实测确认，代码不按这个模拟批量发送，而是每次只发一次、读取真实的新结束时间再判断。配置的“每次至少节省多少秒”仍可让智能模式更早停止付费。

关闭派遣智能省钻后不使用短等及最少节省秒数限制，按剩余时间阈值和预算执行，不受维修智能省钻的开关影响。单段航程上限始终累计，不能每次加速后重置；同一航程也只允许一次省钻短等。

已确认的行军加速若仍高于停止阈值，安排1秒后继续复查；仍以读取到的新结束时间、余额和预算决定是否再发。维修加速确认补满后立即刷新维修占用并重新检查城战派遣，避免额外等一个常规城战检查周期。未知结果仍保留预算，不进入快速重复发送。

在不限制等待时间的情况下，最省钻始终是免费等到结束。本功能优化的是“最多短等W秒”的付费决策，不宣称在任意到达时限、网络耗时下都全局最优。

## 本次修复：迟到推送导致跨队低估费用

离线复现：累计59分钟，两队各剩不到1分钟，每队本次上限10钻。第一队花10钻后，服务端累计变为60；如果 `SCSpeedUp` 迟于舰队/资源回包，旧逻辑会继续按59分钟报价，允许第二队实际花11钻，突破10钻上限。

修复后的行为：

1. 城战与硅矿使用同一连接的共享计费跟踪器，并复用相同分段价格函数。
2. 发送前把本次计费分钟加入本地保守累计值；同步推送追上时不重复计数，迟到的低值不使档位回退。
3. 明确拒绝或明确未发送才撤销本地分钟；不能撤销服务端已报告的累计值。超时或结果未知保留预算及防重记录。
4. 多队只读预览也按队列推进预计累计量，第二队能看到新档位。
5. 累计基线缺失、断线或跨日后尚未同步、当前区服仍有未知维修加速时，用最高档保守预留，不把未知当0分钟；不同连接及区服隔离。
6. 硅矿在最后一次舰队读取之后再复核费用，旧报价低于当前报价时不发送。

预算数字是保守占用，不代表已核实的实际扣款。缺失累计基线或网络耗时使费用估计偏高时可能少加速，不会为了用满预算继续花钻；不能用钻石净余额变化单独推断某笔真实费用。
